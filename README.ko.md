# tui-saver

![tui-saver-show.gif](./tui-saver-show.gif)

[English](README.md)

터미널에서 돌아가는 스크린세이버. 글자만으로 그림을 그린다.

도넛, 정육면체, 불꽃, 지구본, 프랙탈 같은 화면 18가지가 차례로 나온다.
화면이 바뀔 때는 이전 그림이 서서히 흩어지면서 다음 그림이 배어 나온다.

돌아가는 동안 컴퓨터가 잠들지 않게 붙잡아 둔다.
자리를 비워도 절전 모드로 안 넘어가고, 화면도 안 꺼진다.

macOS, Windows, Linux에서 쓸 수 있다.
macOS와 Windows는 따로 준비할 게 없다.
Linux는 `systemd-inhibit`이 필요한데, 데스크톱용 배포판이면 대체로 들어 있다.

## 설치

```sh
npm i -g tui-saver
```

```sh
tui-saver              # 실행
tui-saver --list       # 어떤 화면이 있는지 보기
tui-saver --doctor     # 진짜 안 자고 있는지 확인
tui-saver --help
```

내려받아서 바로 돌려도 된다. 빌드 같은 준비 과정이 없다.

```sh
git clone https://github.com/aciddust/tui-saver
cd tui-saver
node src/main.ts
```

어느 쪽이든 Node 23.6 이상이 필요하다.
그 버전부터 TypeScript 파일을 따로 변환하지 않고 그대로 실행할 수 있다.

아래 설명에서는 `tui-saver`라고 적는다.
clone 해서 쓰는 경우엔 전부 `node src/main.ts`로 바꿔 읽으면 된다.

실행 중에 `?`를 누르면 단축키 목록이 나오고, `q`를 누르면 끝난다.

## 마음에 드는 화면 하나만 계속 보기

기본값은 22초마다 다음 화면으로 넘어간다.

멈추는 방법이 세 가지 있다.

**실행 중에 `f`를 누른다.**
지금 보고 있는 화면을 그대로 고정한다.
상태 표시줄이 `pinned` / `f:unpin`으로 바뀐다.
한 번 더 누르면 다시 돌아간다.
고정한 상태에서도 `n`, `p`로 손수 넘길 수는 있다.

`**--scene <id>`로 시작한다.**
그 화면 하나만 띄운다. 넘어갈 데가 없으니 계속 그대로다.

`**--duration 0`으로 시작한다.**
목록은 그대로 두고 자동 전환만 끈다.
`n`, `p`, `1`~`9`로 직접 넘긴다.

중간 방법도 있다.
`--only globe,fire`처럼 쓰면 고른 화면만 짧게 묶어서 계속 돌린다.

## 알아서 끝나게 하기

기본값은 끝나는 시간이 없다. 일부러 그렇게 뒀다.
잠금은 화면에 이게 떠 있는 동안만 걸려 있고, 화면을 다 덮는 애니메이션은 잊기 어렵다.

그래도 켜 놓고 자리를 떠난 실행은 이유보다 오래 남는다.
그래서 끝나는 시점을 줄 수 있게 했다.

```sh
tui-saver --for 90m        # 90s, 45m, 2h, 1h30m
tui-saver --until 18:00    # 다음 18:00. 오늘 18:00이 지났으면 내일
tui-saver --while 4242     # 그 프로세스가 끝나면 같이 끝난다
```

`--while`이 가장 정직한 쪽이다.

잠들기방지를 그 자체로 켜는 사람은 없다. 뭔가 돌고 있어서 켠다.
`caffeinate -w`가 정확히 그 도구인데 아무도 쓰지 않는다.
자기 규칙이 그걸 버리는 것도 이유 중 하나다.

man 문서에 `-w`는 "utility 옵션과 같이 쓰면 무시된다"고 적혀 있다. `-t`도 마찬가지다.
그래서 `caffeinate -t 60 -w 1234 make`는 둘 다 조용히 버린다.

여기서는 `--while`과 `--for`가 둘 다 실행을 제한하고, 먼저 오는 쪽이 끝낸다.
한쪽을 위해 다른 쪽을 버리지 않는다.

돌고 있지 않은 pid는 거절한다.
`caffeinate -w`가 죽은 pid를 받고 즉시 돌아와 버리는 것과 다르다.

`--while <명령>` 형태는 일부러 만들지 않았다.
`caffeinate <명령>`은 자기가 아무것도 그리지 않으니 터미널을 자식에게 넘길 수 있다.
이 프로그램은 화면을 점유한다. 자식의 출력은 애니메이션에 묻히거나 버려질 수밖에 없다.
명령은 다른 pane에서 돌리고 그 pid를 넘기면 된다.

상태 표시줄이 남은 시간을 세어 준다.
마지막 1분은 색이 바뀐다.
아직 자리에 있으면 `+`로 15분을 더 줄 수 있다.

한도를 안 주면 대신 다른 숫자를 보여 준다.
얼마나 오래 떠 있었는지, 그러니까 컴퓨터를 얼마나 오래 안 재웠는지다.

`caffeinate -t`가 macOS에서 이미 하는 일이다. 아닌 척하지 않겠다.
여기서 더해지는 건 두 가지다.

나머지 두 운영체제에서도 똑같이 된다.
`systemd-inhibit`에는 타임아웃 옵션이 아예 없고 `SetThreadExecutionState`도 없다.

그리고 눈에 보이는 타이머가 생긴다.
아무도 읽을 수 없는 남은 시간은, 결국 감으로 연장하게 된다.

## 배터리를 태우지 않게 하기

`caffeinate`는 지금 뭐에 꽂혀 있는지 모른다.

`-s`가 그나마 전원을 아는 옵션인데, man 문서에 이렇게 적혀 있다.
"이 요청은 AC 전원으로 돌 때만 유효하다."
그러니까 배터리로 돌면 아무 일도 하지 않는다. 경고도 없다.

정작 그게 필요한 상황이 그거다.
안 잘 거라고 믿고 뚜껑 덮고 나간 상황.

그래서 1분에 한 번 충전량을 읽어서 상태 표시줄에 보여 준다.
전원에 꽂혀 있으면 `bat 74% ac`, 배터리로 줄고 있으면 `bat 74%`.

`--battery-floor` 아래로 내려가고 **동시에 배터리로 돌고 있으면**,
10초 동안 경고한 다음 잠금을 풀고 종료한다.

가방 안에서 12%가 된 노트북은, 여기 있는 다른 어떤 기능으로도 막을 수 없는 결과다.

```sh
tui-saver --battery-floor 25   # 기본값 15
tui-saver --battery-floor 0    # 읽고 보여 주기만, 개입은 안 함
```

실제로 줄고 있는 배터리만 센다.
전원에 꽂은 채로 8%에서 작업하는 건 건드리지 않는다.

배터리가 없는 기계는 없다고 보고하고 가드는 아무것도 하지 않는다.
읽는 방법이 없는 운영체제나, 조회가 실패한 경우도 똑같다.
네 경우 모두 답이 같아야 하는 상황이다.

## 컴퓨터가 잠들지 않게 하는 방법

운영체제마다 "지금은 자지 마"라고 알려 두는 수단이 따로 있다.
macOS는 `caffeinate`, Windows는 `SetThreadExecutionState`, Linux는 `systemd-inhibit`을 쓴다.

그런데 이걸 그냥 쓰면 문제가 하나 생긴다.

프로그램이 정상적으로 끝나면 잠금을 풀고 나가지만, 강제로 죽으면 풀 기회가 없다.
`kill -9` 같은 신호는 뒷정리 코드를 아예 실행시키지 않기 때문이다.
그러면 잠금만 남아서 컴퓨터가 영영 안 자게 된다.

그래서 이 프로그램은 잠금을 직접 쥐지 않는다.

대신 잠금을 쥐는 작은 도우미 프로세스를 따로 띄우고, 그 도우미가 이쪽을 지켜보게 한다.
이쪽이 사라지면 도우미가 알아서 잠금을 풀고 종료한다.
도우미가 먼저 죽더라도 운영체제가 프로세스와 함께 잠금을 회수해 간다.

어느 쪽이 먼저 죽든 잠금이 남지 않는다. 이게 설계의 핵심이다.

실제로 띄우는 명령은 이렇다.


| 운영체제    | 명령                                                                   |
| ------- | -------------------------------------------------------------------- |
| macOS   | `caffeinate -dis -w <pid>`                                           |
| Windows | `powershell` → `SetThreadExecutionState`, 이어서 `Wait-Process <pid>`   |
| Linux   | `systemd-inhibit --what=idle -- tail --pid=<pid> -f /dev/null` |


### 어느 기계를 안 재우고 있는지

ssh로 붙어서 실행하면 여기 있는 모든 게 정상 동작한다.
그런데 그중 아무것도 눈앞의 컴퓨터에 관한 게 아니다.
잠금도, 배터리 수치도, idle 타이머도 전부 저쪽 기계 것이다.

그래서 상태 표시줄이 `ssh:<호스트>`를 띄우고 `--doctor`도 호스트를 찍는다.
상태가 보인다는 게 논지인 프로그램이 *누구의* 상태인지를 흐리게 두면 안 된다.

이건 최근까지 생각보다 덜 중요했다.
Linux 백엔드가 로그인 세션 없이는 조용히 실패했고, 그게 정확히 ssh 상황이었으니까.
지금은 동작한다. 그래서 엉뚱한 기계를 안 재우는 일이 실제로 일어날 수 있게 됐다.

### 아무도 안 보고 있을 때

tmux pane은 아무도 볼 수 없는 애니메이션을 계속 돌릴 수 있다.
client가 detach됐거나, 그냥 다른 window를 보고 있는 경우다.

이건 이 프로그램의 실패 방식을 안쪽에서 다시 만난 것이다.
잠금은 걸려 있는데 그걸 알려 주는 표시가 어느 화면에도 없다.

tmux 안에서는 안 보인 시간을 세고, 볼 사람이 생기는 순간 알려 준다.

```
held for 42m with nothing on screen - any key dismisses
```

잠금을 풀지도, 실행을 끝내지도 않는다.
긴 작업을 걸어 두고 일부러 detach하는 건 정상적인 사용이고,
그걸 이유로 실행을 끝내는 건 문제보다 더 나쁘다.

구조적인 답은 여전히 `--for`다. 이건 그런 일이 있었다고 알려 주는 부분이다.

어떤 format 변수를 물어야 하는지가 자명하지 않아서, tmux 3.7b로 직접 재 봤다.


|                     | `session_attached` | `window_active` | `pane_active` |
| ------------------- | ------------------ | --------------- | ------------- |
| detach됨            | 0                  | 1               | 1             |
| 붙어 있지만 다른 window | 1                  | 0               | 1             |
| 붙어 있고 우리 window   | 1                  | 1               | 1             |


그래서 봐야 하는 건 `session_attached`와 `window_active` 둘이다.
`pane_active`는 일부러 보지 않는다.
split된 pane은 active가 아니어도 화면에 보이니까, 그걸 안 보인다고 세면 틀린다.

tmux 밖에서는 창이 보이는지 물어볼 이식성 있는 방법이 없다. 그래서 아무 주장도 하지 않는다.

### 정말 걸려 있는지 아는 방법

도우미가 살아 있다는 건 잠금이 걸렸다는 뜻이 아니다.

요청이 거절될 수도 있고, 이 프로그램 밖의 무언가가 잠금을 풀 수도 있다.
어느 쪽이든 프로세스는 똑같이 멀쩡해 보인다.

그래서 "요청했다"와 "걸려 있다" 사이에 세 가지를 넣었다.

**90초마다 운영체제에 다시 묻는다.**
운영체제가 쓰는 도구를 그대로 쓴다.
macOS는 `pmset -g assertions`, Linux는 `systemd-inhibit --list`.
잠금이 목록에서 사라졌으면 도우미가 살아 있어도 실패로 처리한다.

물어볼 수 없는 것과 아니라고 답한 것은 구분한다.
물어볼 수 없으면 실패가 아니라, 답이 낡은 것으로 둔다.

**죽은 도우미는 한 번 다시 띄운다.**
한 번만이다.
계속 못 뜨는 도우미는 알려야 할 사실이지, 무한히 다시 띄울 일이 아니다.

**실패는 숨길 수 없다.**
상태바는 `h`나 `--no-hud`로 숨길 수 있지만, 맨 위 줄의 경고는 숨길 수 없다.
잠금을 놓친 순간 벨이 한 번 울린다.
약속을 지키지 못한 실행은 종료 코드 1로 끝나고, 그 이유를 stderr에 적는다.

상태바는 근거의 등급을 그대로 보여 준다.
세 운영체제가 같은 근거를 줄 수 없기 때문이다.


| 표시           | 뜻                                                   |
| ------------ | --------------------------------------------------- |
| `awake:os`   | 운영체제가 방금 잠금을 확인해 줬다                       |
| `awake:self` | 도우미가 스스로 걸고 있다고 말한다. 확인해 준 제3자는 없다   |
| `awake:live` | 도우미가 돌고 있다. 아는 건 그것뿐이다                   |
| `awake:FAIL` | 걸고 있지 않다                                     |


Windows는 `awake:self`가 된다.

`powercfg /requests`는 관리자 권한 없이는 요청 목록을 아예 보여 주지 않는다.
권한 없이 Windows에 물어볼 방법이 없다.
그래서 도우미가 대기 루프를 돌 때마다 플래그를 다시 걸고, 성공하면 한 줄을 찍게 했다.
운영체제가 확인해 주는 것보다는 약하고, pid가 살아 있는 것보다는 훨씬 강하다.

이걸 넣으면서 `--doctor`의 고정 대기 3.5초도 사라졌다.
PowerShell이 P/Invoke 껍데기를 컴파일하는 동안은 아직 잠금이 없는데,
그 시간이 얼마인지 몰라서 넉넉하게 기다리던 값이었다.

`--require-awake`를 붙이면 `awake:os`나 `awake:self`에 닿지 못할 때 아무것도 그리지 않고 그냥 끝낸다.
중단되면 안 되는 작업을 감쌀 때 쓴다.

`--doctor`를 붙이면 실제로 잠금을 걸고, watcher가 확인해 줄 때까지 기다린 다음,
어떤 등급의 근거를 받았는지와 운영체제가 그 잠금을 어떻게 보고 있는지를 같이 찍어 준다.
이 문서 말을 믿을 필요 없이 직접 확인할 수 있다.

### 다른 게 뭘 잡고 있는지

"내 잠금이 걸려 있나"에 답해 주는 도구는 남의 잠금도 같이 보여 준다.
그래서 `--doctor`가 그것도 보고한다. 이 글을 쓴 기계의 실제 출력이다.

```
  others holding a lock:
    pid   366  powerd          3h02m  PreventUserIdleSystemSleep, InternalPreventDisplaySleep
    pid 16638  caffeinate      3h01m  PreventUserIdleSystemSleep, PreventUserIdleDisplaySleep
    pid   425  WindowServer    9m40s  UserIsActive
    pid 39289  caffeinate      1m11s  PreventUserIdleSystemSleep
```

오래 잡은 것부터 나온다.
화요일에 누가 켜 두고 잊은 `caffeinate -dis`를 알려 줄 만한 건 이 기계에 달리 없다.

이 프로그램 자신의 잠금과 도우미는 빼고 보여 준다.
도우미는 이름이 아니라 **누구를 대신해** 잡았는지로 알아본다.

판정을 붙이는 건 딱 하나다.

```
    pid 16638  caffeinate      3h01m  PreventUserIdleSystemSleep
      LEAKED: taken for pid 16577, which no longer exists - release it with: kill 16638
```

`caffeinate -w`는 누구를 기다리는지 기록해 둔다.
그래서 그 대상이 죽어 있으면 그건 의심이 아니라 사실이다.

**나이는 아니다.**
처음 만들 때는 한 시간 넘은 걸 다 지적했다.
그런데 처음 돌린 기계에서 macOS 자신의 `powerd`가 `PreventUserIdleSystemSleep`을 세 시간 잡고 있었다.
powerd가 하는 일이 그거다.

그 표시는 아무것도 알려 주지 않으면서 정작 중요한 줄들을 묻어 버렸다.
그래서 지금은 지속 시간을 그냥 보여 주고 정렬만 한다.

운영체제마다 말해 줄 수 있는 게 다르고, 출력이 그걸 숨기지 않는다.


| 조회 명령                        | pid | 프로세스   | 지속시간 | 누구 대신 |
| ------------------------------ | --- | --------- | ------- | ------- |
| `pmset -g assertions`          | 있음 | 있음      | 있음     | 있음     |
| `systemd-inhibit --list`       | 있음 | 있음      | 없음     | 없음     |
| `powercfg /requests`           | 없음 | 경로만    | 없음     | 없음     |


지속 시간이 없는 플랫폼에서는 그 칸을 비워 두지 않고 아예 없애고, 없다고 한 줄 적는다.
Windows는 애초에 관리자 권한이 없으면 답을 안 하고 pid도 알려 주지 않는다.
그래서 우리 도우미를 다른 PowerShell과 구분할 수 없다.

### 직접 확인하기

```sh
node tools/check-awake.ts
```

먼저 세 운영체제의 명령이 제대로 만들어졌는지 훑어본다.
그다음 지금 쓰는 운영체제에서 실제로 한 번 돌려 본다.

버릴 프로세스를 하나 띄워서 그걸 대상으로 잠금을 걸고,
운영체제에 잠금이 걸렸는지 물어보고,
그 프로세스를 강제로 죽인 다음,
도우미가 잠금을 푸는지까지 본다.

**배포할 운영체제마다 한 번씩은 돌려 보는 게 좋다.**
아니면 `.github/workflows/verify.yml`이 대신 해 준다.
push할 때마다 macOS, Windows, Linux 러너에서 이 도구를 돌린다.

Windows에서는 잠금 조회(`powercfg /requests`)에 관리자 권한이 필요하다.
권한이 없으면 실패로 처리하지 않고 그냥 넘어간다.
정작 중요한 강제 종료 테스트는 어디서도 관리자 권한이 필요 없다.

### 운영체제별 상태

세 운영체제 모두 이제 push할 때마다 CI가 확인한다. 이 문서가 원래 하던 말과 달라진 부분이다.

**macOS는 확인을 마쳤다.**
`pmset -g assertions`로 잠금 세 개가 걸린 것을 확인했고, `kill -9` 뒤에 풀리는 것도 확인했다.

**Windows도 확인을 마쳤다.**

작성자에게 Windows 머신도 PowerShell도 없어서 눈으로만 짠 코드였다.
지금은 Windows 러너가 실제로 실행하고, `powercfg /requests`로 요청 목록까지 확인한다.
러너가 관리자 권한으로 도는 덕이다.

읽어서는 절대 못 찾을 것도 하나 나왔다.
PowerShell은 리다이렉트된 stderr를 CLIXML로 직렬화한다.
그래서 실패 이유를 stderr에서 읽으면 `#< CLIXML` 한 줄만 온다.
지금은 watcher가 stdout으로 이유를 보고한다.

대신 실행하지 않고도 확인되는 건 전부 확인했다.
PowerShell에 넘기는 바이트열, 따옴표와 중괄호 짝, 플래그 값을 봤다.
잠금 해제가 `finally` 블록 안에서 도는지도 확인했다.

배포 전에 Windows에서 `tools/check-awake.ts`를 한 번 돌려 보는 게 좋다.

**Linux는 CI로 확인했고, 확인하다가 문제를 찾았다.**

원래는 `--what=idle:sleep`을 요청했다.
로그인 세션이 없는 기계에서는 polkit이 `sleep` 쪽을 "Access denied"로 거절한다.

그런데 `systemd-inhibit` 요청은 원자적이다.
`sleep`이 거절되면 `idle`까지 같이 날아간다.

즉 SSH로 붙었거나, 헤드리스거나, seat이 없는 환경에서는
이 프로그램이 **아무것도 못 잡고 있으면서 잡고 있다고 말하고 있었다.**

지금은 `--what=idle`만 요청한다. 세션이 있든 없든 허용된다.

범위를 좁힌 대가는 생각보다 작다.
`sleep`을 막는다는 건 명시적인 절전까지 막는다는 뜻이다.
뚜껑을 덮거나 `systemctl suspend`를 치거나 전원 버튼을 누르는 것 말이다.
그건 idle 타이머가 가져가는 게 아니라 사람이 요청하는 거다.

macOS도 반대쪽에서 같은 양보를 한다.
`caffeinate`의 `-s`는 문서에 "AC 전원일 때만 유효하다"고 적혀 있다.
배터리에서는 가장 센 옵션이 조용히 빠진다.

잃는 건 하나다.
데스크톱 세션 사용자가 이 프로그램으로 명시적 절전을 막을 수는 없게 됐다.
스크린세이버가 할 일이 아니었다.

### 못 하는 일

**화면 보호기는 못 막는다.**

화면 보호기는 절전과는 별개의 타이머로 돌아간다.
그래서 그냥 두면 이 프로그램 위를 덮어 버린다.

`--defeat-screensaver`를 붙이면 어느 정도 막아 준다.

- macOS — 짧게 `caffeinate -u`를 부른다
- Linux — `xdg-screensaver reset`을 부른다
- Windows — `{F15}` 키를 한 번 누른 척한다

다만 어디까지나 최선을 다해 보는 정도다.
회사 보안 정책으로 걸린 화면 잠금 같은 건 일반 프로그램이 넘을 수 있는 것도 아니고, 넘어서도 안 된다.

이 중에 Windows의 가짜 키 입력만 다른 프로그램에 영향을 줄 수 있다.
그래서 이 코드는 평소엔 실행만 건너뛰는 게 아니라 아예 만들어지지도 않는다.
플래그를 주지 않으면 스크립트에 그 부분이 들어가지 않는다.

**노트북 덮개를 닫으면 못 막는다.**

전원이 연결되어 있고 외부 모니터까지 붙어 있는 경우가 아니면, 어떤 잠금도 덮개 닫힘을 이기지 못한다.

지원하지 않는 운영체제에서도 그림은 그대로 나온다.
다만 잠금을 못 거니까 상태 표시줄에 `awake:n/a`라고 뜬다.

## Windows에서 알아 둘 것

Windows에서만 걸리는 문제가 둘 있었다. 둘 다 고쳤지만 배경은 알아 둘 만하다.

### 색이 안 나오던 문제

터미널이 색을 지원하는지 판단할 때 보통 `TERM`이라는 환경 변수를 본다.
그런데 Windows에서는 이걸 설정해 주는 게 없다.

그래서 "`TERM`이 없으면 색도 없다"는 흔한 규칙 때문에 Windows 터미널이 전부 흑백 판정을 받았다.
24비트 색을 다 지원하는 Windows Terminal까지 같이 걸렸다.

지금은 Windows를 그 규칙보다 먼저 판정해서 컬러를 기본으로 쓴다.
Windows Terminal도, 옛날 콘솔도 Windows 10 1703부터는 컬러를 지원한다.

### 점자 글자가 깨지던 문제

이 프로그램은 화면 일부를 점자 글자로 그린다.
그런데 옛날 콘솔의 기본 글꼴인 Consolas에는 점자 글자가 아예 없다.
그대로 두면 네모 상자만 잔뜩 찍힌다.

글꼴에 어떤 글자가 들어 있는지 터미널에 물어보는 방법은 없다.
그래서 짐작한다.

요즘 터미널이라면 보통 흔적을 남긴다.
`WT_SESSION`, `TERM_PROGRAM`, ConEmu, WezTerm, Alacritty, `TERM` 같은 것들이다.

이런 단서가 하나도 없으면 점자를 쓰는 화면만 반블록 방식으로 바꿔서 그린다.
반블록은 어느 글꼴에나 있는 글자라 안전하다.
나머지 화면은 그대로 나온다.

이 짐작이 틀렸다면 `--braille` 또는 `--no-braille`로 직접 정해 주면 된다.

가장 깔끔하게 보고 싶다면 **Windows Terminal**에 **Cascadia Mono** 글꼴을 권한다.
점자도 컬러도 다 된다.

## 세 가지 그리는 방식

터미널은 글자 단위로만 찍을 수 있다.
그래서 글자 하나를 더 잘게 쪼개 쓰는 요령이 세 가지 있다.

**점자 (braille)**

점자 글자는 점 8개(가로 2 × 세로 4)로 이루어져 있다.
이 점을 픽셀처럼 켜고 끄면 글자 하나에 8배 해상도를 담을 수 있다.

대신 점 하나에는 켜짐/꺼짐만 있고, 색은 글자 단위로 하나뿐이다.
선이나 곡선, 점 뿌리는 그림에 잘 맞는다.

**반블록 (half)**

`▀` 글자는 위쪽 절반만 칠해져 있다.
글자색으로 위 픽셀을, 배경색으로 아래 픽셀을 칠하면 글자 하나에 픽셀 두 개가 생긴다.

해상도는 점자보다 낮지만 픽셀마다 색을 온전히 쓸 수 있다.
색이 부드럽게 변하는 그림에 잘 맞는다.

**ascii**

글자 하나가 픽셀 하나다.
밝기에 따라 `.`, `:`, `*`, `#` 같은 글자를 골라 쓴다.

해상도는 가장 낮지만 색 없이도 형태가 읽히는 유일한 방식이다.

---

화면마다 어울리는 방식이 정해져 있다.
`m`을 누르면 돌아가는 중에 바꿔 볼 수 있고, `--mode`를 주면 전부 한 방식으로 고정된다.

## 실행 옵션

**재생**

```
--scene <id>            이 화면만 보여준다
--only <id,id,...>      고른 화면만 돌린다
--duration <seconds>    화면당 몇 초. 기본 22, 0이면 자동 전환 없음
--transition <seconds>  전환에 걸리는 시간. 기본 0.9
--fps <n>               초당 프레임 수. 기본 32
--speed <n>             전체 속도 배율. 기본 1
--shuffle               순서를 무작위로
--for <90m|2h|1h30m>    이만큼 지나면 전체 실행을 끝낸다
--until <HH:MM>         이 시각이 되면 전체 실행을 끝낸다
--while <pid>           그 프로세스가 끝나면 전체 실행을 끝낸다
```

**모양**

```
--mode <braille|half|ascii>   모든 화면을 한 방식으로 그린다
--palette <id>                색 조합을 고른다
                              mono amber green ice ember magma viridis cyber rainbow
--ramp <classic|soft|blocks|dense>
                              ascii 방식에서 쓸 글자 세트
--color <truecolor|256|mono>  색 지원 여부를 직접 지정한다
--braille / --no-braille      점자 글꼴 짐작을 직접 정한다
                              (위 'Windows에서 알아 둘 것' 참고)
--no-hud                      상태 표시줄을 숨기고 시작한다
```

**잠들지 않게 하기**

```
--no-awake              잠금을 아예 걸지 않는다
--require-awake         잠금을 확인하지 못하면 실행하지 않고 끝낸다
--battery-floor <pct>   배터리로 이 충전량 아래면 실행을 끝낸다. 0이면 끔. 기본 15
--defeat-screensaver    화면 보호기까지 막아 본다
--doctor                운영체제가 잠금을 어떻게 보고 있는지 확인한다
```

색 지원 여부는 `COLORTERM`, `TERM`, `TERM_PROGRAM` 환경 변수로 판단한다.
셋 다 없는 Windows에서는 컬러를 기본으로 본다.
`NO_COLOR`가 설정되어 있으면 그걸 따른다.

색을 끄면 반블록 방식은 ascii로 바뀐다.
색 없는 반블록은 그냥 꽉 찬 네모라서 의미가 없기 때문이다.

## 구현 노트

여기서부터는 코드를 볼 사람을 위한 내용이다.

```
src/core/canvas.ts   픽셀 격자를 글자로 바꾸는 세 가지 방식
src/core/screen.ts   바뀐 부분만 골라내기, ANSI 출력
src/core/raster.ts   투영, 부드러운 선 긋기, 삼각형 채우기
src/core/color.ts    색 조합, 색 압축, 256색 근사
src/core/noise.ts    해시와 작은 난수 생성기
src/core/scene.ts    화면 하나가 지켜야 할 규약
src/awake.ts         운영체제별 잠금 구현과 --doctor
src/ui.ts            상태 표시줄, 도움말, 전환 효과
src/scenes/          화면 하나당 파일 하나
```

### 화면 전체를 다시 그리지 않는다

매 프레임 전체를 새로 출력하면 터미널로 나가는 데이터가 너무 많아진다.
그래서 직전 프레임을 기억해 두고 달라진 구간만 내보낸다.

같은 구간 안에서는 색 지정 명령을 하나로 합치고, 바뀐 쪽 색만 내보낸다.
커서를 다시 옮기는 것보다 싼 경우엔 안 바뀐 짧은 구간도 그냥 같이 내보낸다.

색은 채널당 6비트로 줄여서 쓴다.
그러면 색이 조금씩 변하는 부분에서 이웃한 글자들이 완전히 같은 색이 되어 한 구간으로 합쳐진다.
데이터가 15~30% 줄고, 글자 그림에서는 차이가 눈에 안 보인다.

덕분에 대부분의 화면이 초당 1 MB도 안 쓴다. (132×38 크기, 컬러 기준)


| 화면                       | 프레임당   | 초당 32프레임일 때 |
| ------------------------ | ------ | ----------- |
| `tesseract` (점자, 성긴 편)   | 6 KB   | 0.19 MB/s   |
| `torus` (ascii)          | 17 KB  | 0.52 MB/s   |
| `globe` (반블록)            | 26 KB  | 0.82 MB/s   |
| `plasma` (반블록, 매 픽셀이 바뀜) | 136 KB | 4.2 MB/s    |


`plasma`처럼 화면 전체가 매번 바뀌는 경우가 최악이고, 이건 계속 비싸다.
글자마다 글자색과 배경색이 둘 다 필요한데, 이웃끼리 색이 너무 달라서 합쳐지지도 않는다.

색을 더 뭉개서 쫓아가는 대신, 터미널이 못 따라오면 프레임을 버리는 쪽을 택했다.
느린 터미널에서는 그림이 밀리고 뭉개지는 대신 그냥 프레임 수가 떨어진다.
답답하면 `--fps 20`이나 `--mode ascii`로 데이터를 바로 줄일 수 있다.

### 전환 효과는 픽셀이 아니라 글자 단위로 돈다

그래서 점자로 그린 화면이 반블록으로 그린 화면으로 자연스럽게 녹아들 수 있다.
서로 상대가 어떤 방식으로 그렸는지 알 필요가 없다.

### 궤적을 쌓는 화면은 자기 밝기를 기준으로 조절한다

`lorenz` 같은 화면은 궤적을 쌓아 가며 그린다.
이때 절대 밝기는 점 개수, 프레임 속도, 화면 크기에 한꺼번에 휘둘린다.
한 터미널에서 딱 맞게 맞춰 놓으면 다른 터미널에서는 통째로 하얗게 뭉갠다.

그래서 고정된 밝기 대신, 그 화면에서 지금까지 가장 밝았던 값을 기준으로 삼는다.
그러면 절대 밝기가 아니라 상대적인 밀도가 그려진다. 구조가 보이는 건 그쪽이다.

### 점자는 점 하나에 색이 없다

점자는 점 하나에 켜짐/꺼짐만 있다.
그래서 점이 빽빽하게 몰리면 기준을 넘겨 전부 켜지거나, 못 넘겨 전부 사라지거나 둘 중 하나가 된다.

궤적을 쌓는 화면들이 점자 대신 반블록을 쓰는 이유가 이것이다.

`hilbert`도 마찬가지다.
글자 한 칸에 점이 몇 개나 배정되는지 보고, 곡선을 얼마나 잘게 그릴지 정한다.

## 개발용 도구

```sh
npm test          # node:test, 테스트용 의존성 없음
node tools/snap.ts <sceneId> [--t s] [--cols n] [--rows n] [--mode m] [--frames n]
node tools/bench.ts [--cols n] [--rows n] [--frames n]
node tools/soak.ts
node tools/check-awake.ts
```

`snap`은 한 프레임을 그냥 텍스트로 뽑아 준다.
여기 들어 있는 도형 계산을 터미널 없이 디버깅한 게 이 방법이다.

`bench`는 화면별로 그리는 데 걸리는 시간을 재서 프레임 예산과 견줘 준다.

`soak`은 모든 화면을 모든 방식으로, 일부러 이상하게 잡은 비율까지 여섯 가지 크기에서 돌려 본다.
오류가 나거나, 이상한 숫자가 나오거나, 아무것도 안 그린 화면이 있으면 실패로 잡는다.

`check-awake`는 위 [직접 확인하기](#직접-확인하기)에 설명해 뒀다.

`npm i`를 한 번 하면 `npm run typecheck`에 필요한 도구(typescript, `@types/node`)가 딸려 온다.
프로그램 자체는 여전히 아무것도 필요 없다.

## npm에 배포하기

배포용 패키지에는 원본 소스가 아니라 컴파일한 JavaScript를 싣는다.

Node는 `node_modules` 안에 있는 TypeScript 파일은 실행해 주지 않기 때문이다
(`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`).
전역 설치한 패키지가 정확히 거기 놓이니까, 소스를 그대로 올리면 설치는 되고 실행할 때 죽는다.

```sh
npm run build     # tsconfig.build.json -> dist/
npm publish
```

`build`는 소스가 쓰는 `./foo.ts` 같은 경로를 `./foo.js`로 바꿔서 내보낸다.
`prepack`에 걸어 뒀기 때문에 `npm publish`나 `npm pack`을 하면 알아서 먼저 빌드한다.

저장소에서 작업하는 동안에는 이 과정과 상관이 없고, `dist/`는 커밋하지 않는다.
